# 全屋智能网关与透明代理分流实践：OpenClash/PassWall 混合部署与微信白名单避坑深度拆解

> **【Direct Answer（核心结论速览）】**  
> 旁路由透明网关基于iptables/nftables劫持流量。DHCP指向旁路后，出站经旁路转发，回包若未设伪装易触发非对称路由断网。采用主路由物理网关+旁路TProxy模式+MosDNS域名分流+Keepalived热备组合，既保障全屋高速代理，又杜绝微信转圈与断网风险。

## 一、 底层原理拆解：旁路由流量劫持与非对称路由陷阱

在家庭宽带或极客家庭组网中，为了让智能电视（Apple TV）、游戏主机（PS5、Switch）以及全屋手机、电脑无感享受海外网络加速，许多用户会部署一台运行 OpenWrt 的软路由作为**“旁路透明网关”**。

```
[典型旁路由拓扑与数据流向]
                     ┌───────────────────────┐
                     │ 宽带光猫 (Bridge 桥接) │
                     └──────────┬────────────┘
                                │ WAN
                     ┌──────────┴────────────┐
                     │ 主路由器 (负责拨号/DHCP)│◀───────────┐
                     └─────┬───────────┬─────┘            │
       LAN 流量重定向      │           │ 直连设备默认网关  │
       (Gateway = 旁路IP)  │           │ (网关 = 主路由IP) │ 回包穿透
                           ▼           ▼                  │
                ┌────────────────┐  ┌────────────────┐    │
                │ 旁路由 (OpenWrt)│  │ 普通 IoT 智能设备│   │
                │ 运行 OpenClash │  │  (扫地机/空调等) │   │
                │ MosDNS + 内核  │  └────────────────┘    │
                └───────┬────────┘                        │
                        │                                 │
                        └────── 代理转发 / 海外流量 ──────┘
```

### 1. 流量劫持的运作本质
主路由器负责 PPPoE 拨号获取公网 IPv4，开启 DHCP 服务。管理员将 DHCP 下发的“默认网关”与“DNS 服务器”地址从主路由 IP（如 `192.168.1.1`）修改为旁路由 IP（如 `192.168.1.2`）。终端发起连接时：
* 终端向旁路由发送 TCP SYN 数据包。
* 旁路由利用 Linux 内核的 `iptables` / `nftables` 的 `PREROUTING` 链捕获目的端口为 80/443 的流量，重定向（REDIRECT）至代理内核（Mihomo / Clash Meta）。

### 2. 致命陷阱：非对称路由（Asymmetric Routing）导致断网
如果旁路由与主路由处于同一广播域（同一局域网网段），终端发送的数据经过旁路由发出；但当主路由接收到海外目标服务器的回包时，主路由发现目的 IP 就在本地局域网（终端真实 IP），于是直接将包发回终端：
* 终端发送握手包给了旁路由，却收到了主路由直接甩回来的响应包。
* 终端操作系统的网络栈判定该响应为非法未配对连接，直接发送 TCP RST 强行重置连接，表现为**“全屋设备能 ping 通内网，但任何网页都彻底打不开”**。
* **破解之道**：必须在旁路由防火墙自定义规则中开启 `iptables -t nat -A POSTROUTING -j MASQUERADE`（动态地址伪装），或者在主路由上划分独立的专用隔离 VLAN。

## 二、 全屋网络三大高频致命痛点与深度排障

### 痛点 1：AirDrop、无线打印机与智能家居局域网发现彻底瘫痪
* **故障诱因**：苹果 AirDrop、无线投屏（AirPlay/DLNA）、网络打印机极度依赖 **mDNS（组播 DNS，组播地址 `224.0.0.251`，UDP 端口 `5353`）** 以及 SSDP 协议。透明网关若开启全局 UDP 劫持，代理内核会错误吞噬这些局域网组播包，导致设备间无法相互探测。
* **修复方案**：在 OpenClash 防火墙中强制放行组播与广播地址，显式将 `224.0.0.0/4` 和 `255.255.255.255` 移出代理重定向范围。

### 痛点 2：微信/企业微信发图转圈、提示“当前网络存在风险”
* **故障诱因**：腾讯系通讯工具具有高敏感的风控探针。若透明网关开启了纯 Fake-IP 模式，微信尝试通过内置长连接端口（如 TCP 80/443/8080/14000）握手时，若解析到 `198.18.0.0/16` 的虚假 IP 地址，会判定本地存在中间人劫持；同时微信短视频 CDN 节点若误走海外出口，会直接触发异地保护。
* **修复方案**：在 OpenClash 配置文件中建立严格的**“微信直连专属白名单”**，并在 DNS 分流层将 `*.weixin.qq.com`、`*.wechat.com` 等域名强制指定走国内运营商 DNS 解析。

### 痛点 3：游戏主机（PS5、Switch）NAT 类型恶化为 Strict / Type D
* **故障诱因**：主机联机需要点对点 UDP 穿透（Full Cone NAT）。很多旁路由开启的默认重定向仅针对 TCP，或者代理软件开启了对称型 NAT（Symmetric NAT），导致外界游戏主机无法主动回包。
* **修复方案**：运行模式切换为 **TProxy 混合模式**，在代理内核中开启 `udp-mtu: 1400` 并显式启用 FullCone 模块。

## 三、 MosDNS + OpenClash 组合拳：国内外零污染分流配置实战

为了杜绝 DNS 泄漏、消除 DNS 污染并实现国内域名首包毫秒响应，推荐在旁路由前置部署 **MosDNS 核心**进行预分流：

```yaml
# ==========================================
# OpenClash 关键避坑分流配置文件片段
# ==========================================

# 运行模式推荐：Fake-IP + TProxy (兼顾主机游戏与系统稳定)
mode: rule
log-level: info
ipv6: false # 极度关键：家庭网络若无纯净 IPv6 路由，务必全局关闭

dns:
  enable: true
  listen: 0.0.0.0:7874
  enhanced-mode: fake-ip
  fake-ip-range: 198.18.0.1/16
  # 彻底解决微信/局域网互联异常的 Fake-IP 过滤白名单
  fake-ip-filter:
    - '*.lan'
    - '*.local'
    - 'localhost.ptlogin2.qq.com'
    - '*.wechat.com'
    - '*.weixin.qq.com'
    - '*.qpic.cn'
    - '*.apple.com'
    - '*.icloud.com'
    - '+.nintendo.net'
    - '+.playstation.net'

# 路由规则分流
rules:
  # 1. 局域网与广播流量绝对放行 (直连)
  - IP-CIDR,127.0.0.0/8,DIRECT
  - IP-CIDR,192.168.0.0/16,DIRECT
  - IP-CIDR,224.0.0.0/4,DIRECT
  - IP-CIDR,255.255.255.255/32,DIRECT

  # 2. 腾讯通讯与 Apple 关键服务直连 (彻底规避转圈)
  - DOMAIN-SUFFIX,weixin.qq.com,DIRECT
  - DOMAIN-SUFFIX,qpic.cn,DIRECT
  - DOMAIN-SUFFIX,push.apple.com,DIRECT

  # 3. 游戏主机与国外流媒体智能策略分流
  - DOMAIN-SUFFIX,playstation.com,海外游戏专属
  - DOMAIN-SUFFIX,netflix.com,海外影音专属
  - GEOIP,CN,DIRECT
  - MATCH,兜底代理
```

## 四、 旁路由运行模式实测矩阵与高可用双机热备（Keepalived）

### 1. 三大运行模式性能对比矩阵

| 运行模式分类 | 吞吐带宽损耗 | 微信连通稳定性 | 游戏主机 NAT 等级 | 局域网设备互相发现 | CPU 资源负载 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Redir-Host (旧版重定向)** | 25%~35% (DNS解析延迟大) | 偶现图片转圈 | NAT Type C/D | 正常 | 中等 |
| **Fake-IP (TUN 虚拟网卡)** | 10%~15% (内核态转发) | 需严格配置过滤名单 | NAT Type B | 偶尔阻断广播 | 较高 |
| **Fake-IP (TProxy 混合模式)** | **< 5% (零拷贝透明转发)** | **稳定无感知** | **NAT Type A/B (全穿透)** | **完美兼容** | **优 (硬件利用率高)** |

### 2. 旁路由防宕机：Keepalived 双机热备架构
全屋网络最大的潜在风险在于：**一旦软路由意外死机或重启，全家所有设备瞬间断网**。
* **高可用配置思路**：在主路由与旁路由上配置轻量级 VRRP（虚拟路由冗余协议）。
* 虚拟出一个漂移 IP（如 `192.168.1.254`）作为局域网统一网关。
* 平常旁路由作为 Master 负责透明分流；当旁路由心跳检测超时（死机），主路由将在 **1.5 秒内自动接管虚拟网关**，降级为普通全屋直连上网，实现全屋“不断网”的工业级容灾。

构建全屋智能中枢后，旁路由所挂载的上游出口协议如果稳定性不足，全屋流量仍会遭遇断流。建议参考《[从 TCP BBRv3 到 Hysteria2：晚高峰骨干网 QoS 暴力整形下的抗丢包协议实战演进](/content/wiki/protocols/qos-congestion-control-deep-dive.md)》深入了解底层抗丢包原理。

## 五、 深度技术 FAQ

### Q1：旁路由开启了防火墙动态伪装（Masquerade），为什么会导致主路由后台看到的流量统计全来自于旁路由这一个 IP？
这是 SNAT（源地址转换）的正常物理行为。开启动态伪装后，旁路由为了保证回包能正确原路返回，会将所有局域网设备数据包的源 IP 替换为旁路由自身的 LAN 接口 IP。这会导致主路由的客户端设备列表和行为监控失去精细化统计能力。如果主路由支持静态路由回指（Static Routing），可在主路由上配置针对目标网段的静态路由表，从而在旁路由端安全关闭 Masquerade，恢复单机真实 IP 显示。

### Q2：家庭宽带有公网 IPv6，为什么在旁路由透明代理环境下强烈建议全局关闭 IPv6？
目前绝大多数海外分流规则集与 Fake-IP 架构对 IPv6 的 AAAA 记录处理存在严重的**分流绕过隐患**。当国内终端发起并发查询时，由于 IPv6 解析往往优先于 IPv4，导致部分本应被代理的海外请求直接通过主路由的原生 IPv6 接口裸奔直连，造成 DNS 泄漏或连接被阻断。对于非刚需用户，在旁路由和主路由 LAN 侧关闭 IPv6 DHCP 分配，能大幅提升全屋网络连接的纯净度与稳定性。

### Q3：为什么部分电视盒子在透明网关下观看国内爱奇艺、腾讯视频会提示“您所在的地区无法播放”？
这是典型的 DNS 污染与出口识别偏差。部分电视应用通过特定的反向 IP 检测域名来判断用户所在地。如果这些探测域名被误判进入了 Fake-IP 列表或者匹配到了代理节点的海外出口，视频平台就会将局域网电视误判为海外华人回国访问，从而触发版权封锁。严格在 OpenClash 规则头部添加 `GEOSITE,CN,DIRECT` 并将国内主流长视频域名强制绑定至国内 Local DNS 解析即可彻底消除该报错。
